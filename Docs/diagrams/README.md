# Diagrams

## What is in here

| | |
| :--- | :--- |
| `*.mmd` | **Mermaid source**, extracted from the markdown documents. Plain text, a few hundred bytes each. Windows has no handler for `.mmd`, so double-clicking one will offer to open it with something rather than showing a picture. That is expected — they are not images. |
| `rendered/*.svg` | Vector export, one per diagram |
| `rendered/*.png` | Raster export at 2× scale, for pasting into a Word document |
| `manifest.json` | Generated index of the extracted sources and the document each came from. Regenerated with the `.mmd` files. |

**Edit the markdown, not the `.mmd` files.** The `.mmd` files are generated by
extraction and are overwritten on every run. GitHub renders the fences in the
markdown directly, so the documents are readable without any of this tooling.

## Two things that will break a diagram

Both were real, and both cost time:

1. **A semicolon inside a `Note over` line.** Mermaid's sequence parser treats `;` as a statement separator, so `Note over System: row lock; still pending` is a parse error. Use a comma.
2. **Quotes around a participant alias.** `participant System as ":System"` prints the quote marks literally. Write `participant System as :System`.
3. **An outer `flowchart LR` holding subgraphs that each set `direction TB`.** The subgraphs are laid out along the outer axis, so five of them sit in a row and the export comes out as a ribbon — the use case diagram first rendered at 15020 × 1658, which is unreadable and unusable in a document. Swapping to an outer `TB` with `direction LR` inside each subgraph stacks them and brought the same diagram to 2874 × 1069. Check the exported dimensions, not just that it rendered.

Only 2 of the 8 original diagrams had ever been confirmed to render. Validating
all of them is what found both of the above, plus an extraction bug that had
written the same sequence diagram into four of the five SSD files.

## Regenerating

There is no committed renderer — `@mermaid-js/mermaid-cli` does not work in this
environment (it exits 0 after a long Chromium download without writing a file).
The diagrams were validated and exported with a small offline harness: a local
Node HTTP server serving a page that imports the `mermaid` ESM bundle, renders
every `.mmd`, reports parse errors per diagram, and POSTs the SVG and a 2×
canvas PNG back to disk.

To rebuild it:

```bash
npm install mermaid
```

then serve a page that imports `node_modules/mermaid/dist/mermaid.esm.mjs`,
calls `mermaid.parse()` on each source to catch errors, and `mermaid.render()`
to produce the SVG. Two settings matter for the PNG export:

- `htmlLabels: false` — otherwise labels render into `<foreignObject>`, which a canvas will not draw, and every exported PNG comes out with blank boxes.
- explicit `width`/`height` on the root `<svg>` taken from its `viewBox`, or the canvas has nothing to size itself against.

The whole thing runs offline against the locally installed package. It costs
nothing to re-run and needs no external service.
